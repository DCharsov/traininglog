# TrainingLog — план реализации личного дневника тренировок

Версия: 1.0  
Дата: 14 сентября 2026 года  
Статус: исходная спецификация. Приложение реализовано и опубликовано; актуальный объём и принятые отличия описаны в README.md и docs/release-v2.md. Физическая проверка исключена владельцем 14 сентября 2026; P2 — отдельный backlog.

## 1. Задача и ограничения

Сделать собственное мобильное веб-приложение для одного владельца: тренироваться по своей программе, записывать каждый подход, видеть предыдущие рабочие веса и историю. STNDRD — ориентир по сценарию использования, не источник кода, фирменного оформления, видео или закрытого контента.

Главный сценарий: открыть приложение в зале → продолжить/начать тренировку → увидеть предыдущие подходы → записать вес и повторения → подтвердить подход → запустить отдых → завершить тренировку. Повторить при плохом интернете, блокировке экрана и перезапуске приложения без потери уже подтверждённых локальных записей при сохранном хранилище устройства.

Исходные пользовательские требования:

- Личное использование, приоритет телефона; удобно редактировать программу также с компьютера.
- Предыдущий опыт STNDRD и тренировок по bro split. Точный состав программы пользователь предоставит отдельно.
- Главный приоритет — учёт весов, повторений и подходов, а не социальные функции.
- Поддержать произвольную программу, а не зашивать предложенную ранее схему A/B или обязательные пять тренировок в неделю.
- В приседе в Смите пользователь учитывал только блины, без грифа. На конкретном горизонтальном блоке встречались деления 40 и 47 кг. Нельзя предполагать одинаковые шаги веса на всех тренажёрах.
- Был перерыв и краткий эпизод боли в пояснице. Приложение не назначает безопасные веса, не диагностирует и не повышает нагрузку автоматически.
- Разработка на Windows Native; WSL, Ubuntu и Docker для локального запуска не требуются.

Неизвестные параметры: точные дни bro split, упражнения, тренажёры, доступные деления, подходы/повторения и сохранившаяся история. Отсутствующие факты не заполнять догадками. Демонстрационные записи маркировать и хранить отдельно от настоящих тренировок.

## 2. Формат продукта

PWA: адаптивный сайт с иконкой на домашнем экране, самостоятельным окном и офлайн-доступом к уже загруженным данным. На iPhone предусмотреть инструкцию установки через меню «Поделиться», а не рассчитывать на единый программный install prompt. Для реального мобильного PWA-теста нужен HTTPS; localhost на компьютере не означает, что обычный HTTP-адрес компьютера в локальной сети подходит телефону. [2]

Рекомендуемый вариант поставки: один веб-клиент, один ASP.NET Core backend, одна база SQLite и один домен. Клиент и API публикуются с одного origin. Обязательных платных SDK и подписок на фитнес-контент нет; домен/сервер могут иметь собственную стоимость. Конкретный хостинг выбирать перед развёртыванием.

### Приоритеты

**P0, до перехода на приложение как основной дневник:** запись подходов; предыдущие результаты; редактор собственных программ; история; возобновление активной сессии; офлайн-журнал; JSON-экспорт/восстановление; серверное хранение с авторизацией; понятный статус синхронизации.

**P1, после надёжности P0:** графики; пользовательские рекорды; мягкие подсказки по прогрессии; CSV; дополнительные фильтры; качественный desktop-редактор.

**P2:** замеры тела; фото; суперсеты; дроп-сеты; официальные адаптеры импорта; дополнительные пользователи; уведомления; интеграции с носимыми устройствами.

**За рамками:** платёжная система, магазин программ, социальная сеть, подсчёт питания, автоматический тренер, большая видеобиблиотека, микросервисы, Kafka/RabbitMQ/Redis/Kubernetes. Не подключать AI к критическому сценарию записи и хранения тренировок.

## 3. Пользовательские сценарии

### 3.1. Первичная настройка

Владелец входит в приложение, задаёт килограммы и настройки отображения, создаёт программу и дни. Для упражнений указывает название, вариант выполнения и профиль оборудования. После первого успешного получения программы и истории приложение показывает готовность к офлайн-использованию. Первый вход на новом устройстве требует сети.

Для раннего прототипа до готовности редактора допустим импорт вручную подготовленной собственной программы из проверяемого JSON. Это не автоматический импорт из STNDRD.

### 3.2. Начало занятия

На главной странице видна активная сессия или предложенный следующий день программы. Предложение не блокирует выбор другого дня. Программа работает как последовательность дней; календарное расписание опционально. Пропуск понедельника не удаляет тренировку и не сбрасывает цикл.

При начале занятия создаются клиентский UUID, снимок версии программы, порядок упражнений и целевые подходы. Разрешена одна активная сессия на основном устройстве. Если другое устройство офлайн создало свою сессию, сервер не удаляет её молча: после синхронизации пользователь видит обе и разрешает ситуацию.

### 3.3. Запись подхода

Возле текущего упражнения постоянно отображаются дата и подходы предыдущего сопоставимого занятия. Ввод: вес, повторения, необязательный RIR, тип подхода и заметка. Удобные действия: повторить предыдущие значения, увеличить/уменьшить по настройке оборудования, добавить подход, пропустить, отменить последнее подтверждение.

Предыдущие цифры — подсказка, а не выполненный результат. Нельзя создавать выполненные подходы при открытии экрана, автозаполнении или завершении тренировки.

Каждый вводимый черновик сохраняется локально. Подтверждение подхода выполняет атомарную локальную запись результата и очереди синхронизации. Только после успешной транзакции показывать «Сохранено на устройстве». При сбое записи показывать ошибку и сохранять введённое значение в интерфейсе; не утверждать, что запись сохранена.

Повторное нажатие «Готово» не создаёт новый подход и повторно не запускает таймер для того же подтверждения. Завершённый подход можно исправить; изменение получает новую ревизию.

### 3.4. Завершение и история

Пользователь может завершить неполную тренировку. Пустые подходы остаются пропущенными, а не становятся нулевыми или выполненными. Отдельно различать завершённую неполную сессию и отменённую/брошенную сессию.

История содержит исходные значения и снимок контекста. Изменение шаблона программы не меняет старые тренировки. Исправление исторической записи допустимо явно; после него пересчитываются связанные графики и рекорды.

При открытии приложения после перезапуска сначала восстановить активную сессию из локальной базы, затем синхронизировать. Не ожидать сеть ради отображения уже записанных подходов.

## 5. Программа и библиотека упражнений

Поддержать любой набор дней и циклический порядок. Пример «Грудь / Спина / Ноги / Плечи / Руки» — лишь пример структуры bro split, не назначение частоты.

Для элемента дня хранить:

- упражнение и оборудование;
- порядок;
- целевое количество рабочих подходов;
- диапазон повторений или длительность;
- необязательный целевой RIR;
- отдых в секундах;
- заметку и необязательную ссылку на внешнюю технику выполнения.

Редактирование программы в первой серверной версии — онлайн. Офлайн доступны уже загруженные программы для начала тренировок и полноценный журнал сессий. Это сознательное сокращение области синхронизации, а не скрытое ограничение.

Замена упражнения во время занятия должна предлагать два разных действия: «Только сегодня» и «Изменить программу для будущих тренировок». Второе требует сети и создаёт новую версию программы. Уже начатая сессия остаётся на своём снимке.

Архивирование упражнения не удаляет историю. Переименование не создаёт новый результат. Изменение смысла варианта или способа учёта веса создаёт новый профиль сравнения.

## 6. Вес и сопоставимость — центральные правила

### 6.1. Режимы учёта

| LoadMode | Значение введённого веса |
|---|---|
| BarbellTotal | Общий вес штанги с грифом |
| SmithPlatesOnly | Только блины; гриф не учитывается |
| PerDumbbell | Вес одной гантели |
| MachineStack | Значение на стеке конкретного тренажёра |
| AddedBodyweight | Дополнительное отягощение при упражнении с собственным весом |
| AssistedBodyweight | Величина помощи тренажёра, а не поднятая нагрузка |
| BodyweightOnly | Только собственный вес; внешняя нагрузка не вводится |

Не считать автоматически неизвестную массу или противовес грифа Смита. Не переводить Смит в свободную штангу. Не суммировать гантели без явно определённого режима учёта. В AssistedBodyweight уменьшение помощи отличается от увеличения поднимаемого веса и не обрабатывается обычным алгоритмом прогрессии.

Вес хранить целым числом граммов (`loadGrams`), показывать в кг. Например, 72,5 кг → 72500. Парсер принимает запятую и точку; незавершённый ввод «72,» сохраняется как черновик, а не превращается в испорченное подтверждённое значение. Не использовать двоичный float для канонического веса. Ноль и отсутствие значения различаются; у bodyweight-упражнения нулевая дополнительная нагрузка может быть корректной.

### 6.2. Профиль сравнения

Сопоставимые результаты имеют одинаковые ExerciseVariantId, EquipmentProfileId и LoadMode. Для односторонних упражнений фиксировать правило повторений «на сторону» и при необходимости сторону отдельной строкой. Разминку отделять от рабочих подходов.

В профиле оборудования задавать шаг веса либо точный список доступных значений. Если известны только 40 и 47 кг, нельзя автоматически выдумывать остальные деления. При неизвестном шаге оставить свободный ввод и отключить автоматический расчёт следующего веса.

Предыдущее выполнение сначала искать в том же элементе программы; при его отсутствии — среди сопоставимых упражнений других дней с явным названием источника. Всегда показывать дату. Не использовать частично совпавшее название упражнения как единственный ключ.

## 7. Таймер отдыха

Хранить `restEndsAtUtc` локально; отображаемый остаток вычислять по текущему времени. `setInterval`/`setTimeout` служат только для перерисовки, а не как источник истины. Браузерные таймеры могут задерживаться, особенно в неактивном контексте. [7]

Действия: +30 секунд, −30 секунд, пропустить, запустить заново. Исправление веса уже завершённого подхода не должно неожиданно перезапускать отдых. После возвращения на экран пересчитать остаток.

В MVP гарантируем восстановление состояния таймера, а не точный звуковой сигнал при заблокированном iPhone. Не обещать нативный офлайн-будильник. Не делать Background Sync обязательным условием сохранения: поддержка API ограничена. [6]

## 8. История и аналитика

Начать с трёх представлений: полная история сессий; история подходов одного упражнения; повторения при выбранном весе во времени. Потом добавить максимальный записанный вес при заданном минимуме повторений и недельное количество выполненных рабочих подходов.

Правила:

- Основной источник — фактически подтверждённые подходы, не план.
- Незаконченный ввод не участвует в статистике.
- Отменённые тренировки по умолчанию исключены; завершённые неполные включают реально выполненные подходы.
- Сравнение ограничено профилем нагрузки. Изменение профиля создаёт отдельный ряд.
- `Σ(вес × повторы)` допустим как условный учётный показатель одного сопоставимого упражнения, но не универсальная оценка качества тренировки или точная механическая работа.
- Для AssistedBodyweight и BodyweightOnly не выводить вводящий в заблуждение общий тоннаж.
- Не смешивать прямые и косвенные подходы по мышцам без явной методики. В первой версии достаточно статистики по упражнениям.
- e1RM не нужен в MVP. Если появится позже, показывать как оценку с указанием модели, а не измеренный максимум.

### Подсказки по прогрессии, P1

Они не изменяют программу сами. Для простого режима одинакового веса предложение следующего доступного значения допустимо только после двух сопоставимых завершённых тренировок: все запланированные рабочие подходы достигли верхней границы повторений; известный RIR удовлетворяет пользовательской цели; нет отметки дискомфорта; не менялся профиль оборудования; известен шаг веса. Неизвестный RIR — неизвестность, а не разрешение на прибавку.

После настраиваемого длительного перерыва показывать дату последнего выполнения и отключать автоматическое предложение повышения. Это правило интерфейса, не медицинский срок адаптации. При разных весах по подходам, помощи тренажёра или неизвестных данных в первой версии не пытаться угадать прогрессию.

## 9. Техническая архитектура

| Область | Выбор |
|---|---|
| UI | React + TypeScript, сборка Vite, обычный адаптивный CSS |
| Локальная база | IndexedDB через Dexie; чтение реактивными запросами |
| PWA | Manifest и service worker с версионированным app shell |
| Backend | ASP.NET Core 10, Minimal APIs, EF Core 10 |
| Серверная БД | SQLite на постоянном локальном диске одного экземпляра приложения |
| Вход | ASP.NET Core Identity и cookie, одна учётная запись владельца |
| Тесты | xUnit; Vitest; Playwright; ручные проверки реального iPhone |

.NET 10 — LTS-линия с поддержкой до ноября 2028 года. Зафиксировать поддерживаемый SDK в `global.json`, версии frontend-зависимостей в lockfile и совместимый Node LTS для выбранного Vite. [3, 12]

Dexie используется как библиотека локального IndexedDB, не как платный Dexie Cloud. Обычный Dexie сам по себе не синхронизирует данные между телефоном и компьютером; серверный протокол реализуется отдельно. [4]

SQLite выбран как достаточное проектное решение для одного пользователя и одного серверного процесса. Хранить файл вне `wwwroot` и вне временной/эфемерной файловой системы. При необходимости горизонтального масштабирования пересмотреть БД; заранее PostgreSQL не обязателен.

У SQLite/EF Core есть ограничения по автоматически генерируемым concurrency tokens и отдельным типам запросов. Использовать собственный целочисленный `serverVersion`, UTC и целые значения веса. Проверять миграции на копии настоящей базы. [8]

| WorkoutSession | UUID, владелец, программа/версия, статус, UTC-время, локальная дата/зона, заметки, serverVersion |
| WorkoutExercise | UUID, SessionId, ссылки и снимки названия/нагрузки/целей/порядка |
| SetRecord | UUID, упражнение сессии, порядок, тип, статус, loadGrams, reps/duration, RIR, заметка, время |
| OutboxEntry | Локальный UUID операции, SessionId, неизменяемый отправляемый payload, baseVersion, состояние повторов |
| AppliedOperation | Серверный владелец + operationId, hash запроса, сохранённый ответ |
| ChangeEntry | Серверный монотонный sequence, тип/ID объекта, версия, tombstone |

Времена — UTC, плюс фиксировать локальную дату тренировки и часовую зону на момент начала. Тогда поездка не переносит старую тренировку на другой день. Продолжительность не рассчитывать по локальным часам без учёта смены зоны.

`WorkoutSession` — агрегат: его снимок включает упражнения и подходы. Шаблоны и справочники версионируются отдельно; удаление справочника не каскадирует в журнал.

RIR, заметки, признаки дискомфорта необязательны. Проверка Completed-подхода зависит от trackingMode: для нагрузки+повторов требуются соответствующие поля; для планки — положительная длительность. Отрицательные нагрузки и повторения отклоняются. Допустимые границы валидируются одинаково клиентом и сервером.

## 11. Офлайн и синхронизация

### 11.1. Что хранится на устройстве

App shell, активная версия программы, справочники, загруженная история, активная сессия, таймер, черновики и очередь изменений. React state — не единственное хранилище.

IndexedDB может быть очищен браузером или самим владельцем; постоянство нельзя трактовать как абсолютную гарантию. Запрашивать persistent storage, показывать результат, но всё равно иметь серверную копию и экспорт. [5]

### 11.2. Протокол сессий без сложного CRDT

В MVP синхронизируются полные ограниченные по размеру снимки WorkoutSession. Это проще, чем независимо упорядочивать запросы создания упражнений, изменения веса и завершения занятия.

1. Изменение сессии и dirty/localRevision фиксируются локально атомарно.
2. Синхронизатор создаёт неизменяемый запрос снимка, фиксируя operationId, payload и baseVersion. После первой попытки этот запрос не меняется.
3. Для одной сессии одновременно отправляется не больше одного запроса. Ввод новых подходов продолжается локально в более новой localRevision.
4. Сервер сначала проверяет обработанный operationId. Такой же ключ с тем же payload возвращает сохранённый ответ, а не повторяет запись. Такой же ключ с другим payload — ошибка.
5. Если операция новая, сервер атомарно проверяет expected/baseVersion, сохраняет весь снимок, увеличивает serverVersion, добавляет change sequence и ответ идемпотентности.
6. Только после подтверждения клиент помечает именно отправленную ревизию синхронизированной. Более свежая локальная ревизия не стирается ответом сервера.
7. Если после отправки произошли новые изменения, формируется следующий снимок уже с подтверждённой базовой версией.
8. При конфликте версий сервер отдаёт конфликт и актуальную версию. Клиент сохраняет локальный и серверный варианты, останавливает автоматическую отправку этой сессии и предлагает явное разрешение.

Для создания: UUID генерируется на клиенте, baseVersion=0 означает отсутствие серверной записи. Повтор создания с тем же operationId не дублирует тренировку.

Обычное редактирование справочников/программ онлайн тоже использует проверку версии. Для загрузки удалённых изменений — `GET /api/changes?after=cursor` с монотонным серверным курсором, пагинацией и tombstones. Не синхронизировать по ненадёжному времени устройства. Не заменять локально изменённую сессию пришедшим remote-снимком без проверки.

При устаревшем курсоре после восстановления сервера вернуть признак необходимости bootstrap; сохранять локальные несинхронизированные сессии и разрешать конфликты, не очищать их автоматически. В bootstrap включить идентификатор поколения серверной базы.

### 11.3. Когда синхронизировать

При открытии приложения, возвращении на экран, появлении сети, ручном действии и периодически во время активного использования. Событие `online` — повод попробовать запрос, а не доказательство доступности сервера. Backoff при сетевых ошибках; 401 требует повторного входа без потери очереди; конфликт не лечится бесконечным retry.

На фоне синхронизация является дополнительной оптимизацией при поддержке браузером. Не обещать, что закрытый офлайн-iPhone отправит данные без повторного открытия. [6]

Статусы для пользователя: «Сохранено на устройстве», «Есть несинхронизированные изменения», «Синхронизировано», «Нужен вход», «Конфликт», «Ошибка локального сохранения».

### 11.4. Вкладки и обновления

Для нескольких вкладок одного origin выбрать активного редактора сессии через поддерживаемую блокировку либо атомарный lease в IndexedDB. Остальные вкладки открывают активную сессию в режиме чтения с возможностью явного перехвата после проверки. BroadcastChannel допустим для уведомлений, но не как единственная гарантия записи.

Не активировать новую версию service worker с принудительной перезагрузкой посреди подхода. Обновление предлагать в безопасной точке. Миграции IndexedDB должны сохранять pending-записи. При невозможности миграции — режим восстановления/экспорта, не очистка базы.

## 12. API первой серверной версии

Все маршруты с данными требуют авторизации владельца. OwnerId брать из серверной сессии, не доверять полю клиента.

| Маршрут | Назначение |
|---|---|
| POST /api/auth/login, /logout | Вход/выход; защита по выбранной cookie/antiforgery-схеме |
| GET /api/bootstrap | Справочники, программы, страницы истории, поколения/курсоры |
| GET/POST/PUT /api/exercises | Каталог и профили упражнений; онлайн-редактор |
| GET/POST/PUT /api/equipment | Профили тренажёров и конвенции веса |
| GET/POST /api/programs | Список и создание |
| POST /api/programs/{id}/versions | Новая версия программы с проверкой предыдущей версии |
| PUT /api/sessions/{id} | Снимок сессии; operationId/baseVersion; идемпотентность |
| GET /api/sessions | История с курсорной пагинацией |
| GET /api/changes?after=... | Инкрементальные изменения и удаления |
| GET /api/export | Серверный экспорт; локальный экспорт дополнительно включает несинхронизированные записи |

Точные DTO описать в OpenAPI; типы клиента генерировать из контракта. Общий формат ошибок должен различать валидацию, авторизацию, конфликт, сетевой сбой и несовместимость схемы. Установить разумные лимиты размера запроса и числа подходов, чтобы случайный повреждённый импорт не загрузил бесконечный массив.

Не требовать отдельного онлайн POST /complete после успешной офлайн-тренировки: completed status и время завершения входят в тот же атомарный снимок.

## 13. Безопасность и резервирование

ASP.NET Core Identity с одной учётной записью, без публичной регистрации. Cookie Secure/HttpOnly/SameSite; HTTPS; проверка antiforgery для изменяющих запросов; ограничения попыток входа. Пароли хешировать штатным механизмом Identity. Секреты и ключи Data Protection хранить вне репозитория и сохранять между перезапусками сервера. [9, 10]

Не хранить JWT/пароли в localStorage. API не кэшировать service worker как общедоступную статику. Локальный журнал хранится намеренно для офлайн-работы, но это не обещание шифрования данных от владельца разблокированного устройства. При выходе предупреждать о несинхронизированных данных и предлагать экспорт перед очисткой локального профиля.

Никакой аналитики третьим сторонам по умолчанию. В логи писать ID операций и ошибки, а не пароли, cookie и полный текст личных заметок.

### Копии

Локальный JSON-экспорт: schemaVersion, все собственные программы/профили, сессии, реальные состояния подходов, необходимые снимки; без cookie и серверных секретов. Включает ещё не синхронизированные результаты. CSV — отдельная плоская выгрузка, не замена полной резервной копии.

Импорт: проверка версии/структуры, предварительный просмотр, обнаружение конфликтов UUID, подтверждение замены, резервная копия перед операцией, атомарное применение. Восстановление не должно повторно исполнять старые сетевые операции как новые тренировки. Для первой версии допустим только явный restore всего набора; merge разных архивов отложить.

Сервер: ежедневная согласованная резервная копия SQLite, несколько предыдущих версий и отдельное от сервера место хранения. Для живой базы использовать Backup API или VACUUM INTO, а не просто копировать открытый .db без учёта согласованности. [11]

Проверять восстановление на чистой среде. Бэкап не защищает подход, который ещё не синхронизирован; пользователь должен видеть этот статус.

Оценка, не обещание срока: прототип основного сценария порядка 8–16 часов; офлайн-бета с экспортом примерно 30–50 часов суммарно; личная серверная версия с конфликтами, резервированием и проверками примерно 70–120 часов суммарно. ## 16. Что передать агенту реализации

Начать с этой спецификации и TL-01–TL-03. Не реализовывать весь backlog одним неподконтрольным изменением. Каждый этап заканчивается работающим сценарием, тестами, списком изменений и известными ограничениями.

Демонстрационные результаты допустимы только в отдельном demo seed. Production seed не содержит вымышленных тренировок и назначенных по умолчанию тяжёлых весов. Пользовательские дни и упражнения добавляются из его данных.

Порядок первого инкремента: определить LoadMode и snapshots → IndexedDB → экран подходов → восстановление → история предыдущего выполнения → тесты. Лишь затем усложнять визуал, серверную синхронизацию и рекомендации.

## 17. Данные программы, которые предстоит получить

Для каждого дня: название и порядок; упражнения; рабочие подходы и диапазон повторений; привычный отдых; известные рабочие веса и способ их учёта; особенности тренажёра/выполнения. Отсутствующий вес допустим — поле остаётся пустым до реальной записи.

Если у пользователя есть официальный CSV/JSON истории, его формат сначала изучается, затем создаётся отдельный адаптер. Доступность экспорта или API STNDRD на данном этапе не подтверждена. Не запрашивать чужие пароли, не проектировать обход подписки и не переносить закрытую видеобиблиотеку.
