# Apple Watch: план бесплатной личной версии

Дата: 24 сентября 2026 года. Статус: план реализации; приложение watchOS и изменения API ещё не написаны. Начинать исполнение на Mac с этапа 0.

## 1. Цель и выбранный вариант

Вести уже начатую тренировку с Apple Watch Series 8/9: видеть упражнение, вводить вес и повторы, подтверждать и пропускать подходы, отсчитывать отдых. Телефон можно убрать в карман. Записи должны переживать потерю сети и перезапуск приложения.

Ограничения владельца: есть доступ к Mac; платная регистрация Apple Developer Program из РФ не получается; ежегодную подписку оплачивать не планируется. Поэтому делаем личную сборку через **Xcode Personal Team**, без App Store и TestFlight.

Бесплатная подпись действует **7 дней с выдачи профиля**, после чего требуется переподписать и заново установить сборку. Обычный Apple Account и бесплатное соглашение разработчика всё равно нужны. Отказ в платной регистрации не доказывает отказ Personal Team, но работоспособность конкретного аккаунта нужно проверить на настоящих часах до основной разработки. Это ограничение Apple, которое наш код не отменяет. [Apple: Personal Team](https://developer.apple.com/help/account/basics/about-your-developer-account/)

Выбранная архитектура: самостоятельное приложение watchOS на SwiftUI, локальная запись на часах, HTTPS к существующему ASP.NET Core API. На iPhone остаётся текущая PWA. Apple поддерживает приложения только для часов и доступ к серверу через URLSession; сеть может идти через спаренный iPhone, Wi-Fi или сотовую связь часов. Это не прямое управление Safari через Bluetooth. [Независимые приложения](https://developer.apple.com/documentation/watchos-apps/creating-independent-watchos-apps), [сеть часов](https://developer.apple.com/documentation/watchos-apps/keeping-your-watchos-app-s-content-up-to-date)

Для первичной привязки и передачи тренировки нужен доступ к серверу. После полной загрузки тренировки часы записывают подходы без сети; телефон увидит их после отправки с часов и своей синхронизации. Начать совершенно новую тренировку офлайн на часах в первой версии нельзя.

## 2. Что уже есть в проекте

План основан на прочитанном коде, а не только на README:

- `apps/web/src/domain.ts`: Session, UUID упражнений/подходов, целые граммы, повторения и длительность, левая/правая сторона, RIR, режимы веса, абсолютное `restEndsAt`.
- `apps/web/src/workoutFlow.ts`: порядок подходов, явные и распознанные по заметкам суперсеты, выбор следующего незаполненного подхода.
- `apps/web/src/setValidation.ts`, `restDefaults.ts`, `workoutUx.ts`: валидация, отдых и выбор текущего подхода. Текущий выбор интерфейса хранится отдельно от Session.
- `apps/web/src/data.ts`: IndexedDB **v4**, локальные ревизии и очередь; более ранние разделы README описывают v3.
- `apps/web/src/sync.ts`: полные снимки документов, `operationId`, `baseVersion`, `generation`, неизменяемый повтор запроса, сохранение конфликтующих копий.
- `apps/web/src/useSyncController.ts`: синхронизация при возврате/подключении сети и примерно раз в 30 секунд в открытом приложении.
- `apps/api/Program.cs`, `Store.cs`, `Validation.cs`: один владелец, Identity-cookie, глобальная проверка CSRF для изменяющих запросов, SQLite, один writer, транзакция снимка/версии/журнала/квитанции.
- `apps/api/openapi.json`, `tools/api-contract`: контракт v2 и генерация типов веб-клиента.

Повторно используем формат Session, UUID, правила записи, защиту повторов и серверную историю изменений. Не переносим в часы весь React-интерфейс и не заменяем текущую базу.

В дереве на момент планирования уже были чужие/ранее сделанные изменения в `apps/api/packages.lock.json` и `docs/deployment.md`. При переносе сохранить их; не сбрасывать и не считать частью этой задачи без проверки.

## 3. Как будет выглядеть работа пользователя

1. На Mac установить бесплатную сборку на часы и привязать их к дневнику одноразовым кодом.
2. На телефоне открыть дневник, войти в серверную синхронизацию и начать тренировку обычным способом.
3. Выбрать оборудование для упражнений, где оно обязательно. Нажать «Продолжить на часах».
4. PWA сохраняет ввод, отправляет тренировку на сервер и временно блокирует её редактирование. Часы загружают полную копию и подтверждают приём.
5. Дождаться на часах надписи «Тренировка загружена». Только после этого можно рассчитывать на работу без сети.
6. Отмечать подходы на часах. Успешное нажатие сначала сохраняется локально, затем показывается следующий подход. При сети изменения отправляются на сервер.
7. Телефон показывает результаты, которые дошли до сервера, и время последней синхронизации. Закрытая PWA не обязана обновляться в фоне.
8. На часах закончить тренировку либо выбрать «Вернуть на телефон». Обычный возврат управления завершается после доставки всех записей и подтверждения сервера.

Возврат без сети не объявлять успешным: показывать «Записи сохранены на часах. Возврат ждёт соединения». Для сломанных/недоступных часов предусмотреть отдельное восстановление управления с сохранением конфликтующих копий.

## 4. Этап 0 — проверить бесплатную установку до основной работы

Результат этого этапа важнее прототипа интерфейса. Порядок на Mac:

1. Прочитать инструкции репозитория и этот план; проверить изменения файлов.
2. Записать версии macOS, Xcode, iOS и watchOS, модель и размер часов. Подобрать совместимый стабильный Xcode по официальной матрице, без требования установить последнюю версию любой ценой. [Требования Xcode](https://developer.apple.com/xcode/system-requirements/)
3. Открыть Xcode, войти обычным Apple Account, принять необходимые бесплатные соглашения. Проверить появление Personal Team. Платное вступление не оформлять.
4. Спарить устройства с Xcode, включить Developer Mode там, где Xcode требует, подтвердить доверие на устройствах. Личные пароли, коды 2FA и системные подтверждения вводит владелец. [Developer Mode](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device)
5. Создать минимальный watch-only target: SwiftUI, экран с кнопкой и локальным счётчиком. Сразу выбрать постоянные уникальные bundle identifiers для будущего приложения и автоматическую подпись Personal Team.
6. Не включать HealthKit, CloudKit, APNs, Sign in with Apple и другие необязательные capabilities. Не утверждать, что какая-либо capability бесплатна/недоступна, только по пустым ячейкам HTML-выгрузки документации: проверить реальное подписание target. [Матрица возможностей watchOS](https://developer.apple.com/help/account/reference/supported-capabilities-watchos)
7. Выполнить Run на **физических часах**. Проверить повторный запуск без debugger, сохранение счётчика после закрытия, HTTPS-запрос к `/training/api/health` без отправки тренировочных данных.
8. Поставить локальное уведомление на 60 секунд, опустить запястье/открыть циферблат, проверить фактическое поведение. Отказ в уведомлениях не должен мешать записи подходов.
9. Повторно установить сборку поверх прежней с теми же team/bundle ID и проверить сохранность счётчика. Найти фактический срок профиля, если он доступен через артефакты Xcode.

Критерий продолжения: реальная бесплатная сборка запускается без debugger, хранит данные и делает HTTPS-запрос. Симулятор не подтверждает возможность подписи, установки и уведомлений на часах.

Если Personal Team не даёт установить даже минимальный target: сохранить точную ошибку, проверить соглашения, совместимость Xcode, лимиты бесплатного аккаунта и состояние сервисов Apple. Не добавлять платную регистрацию, смену страны на вымышленные данные, сторонние сертификаты или обещания обхода. Дальнейшее тестирование в симуляторе возможно, но полезная установка на часы остаётся нерешённой; основную серверную интеграцию до её решения не начинать.

## 5. Объём первой пригодной для зала версии

### Часы

- Экран подключения: одноразовый код, статус связи, доступная для приёма тренировка.
- Экран подхода: русское название, номер подхода, цель, режим учёта веса, сторона, введённые вес/повторы либо секунды. Длинные названия переносятся.
- Кнопки изменения значений и Digital Crown для явно выбранного поля. Не менять вес случайным прокручиванием основного экрана. Собственный вес не требует фиктивных «0 кг».
- Шаг веса и доступные деления берутся из профиля упражнения. Если шаг не задан, дать явный ввод, не назначать автоматически 2,5 кг.
- Основная кнопка «Выполнено», вторичные «Пропустить», «Исправить последний подход», выбор упражнения из короткого списка. Повторное нажатие не создаёт новую запись.
- Обычные подходы, разминочные/рабочие статусы, длительность, левая/правая стороны и суперсеты поддерживаются до использования реальных программ. Они уже встречаются в дневнике.
- Необязательный RIR 0–10 через дополнительный экран. Существующие заметки и все неотображаемые поля сохраняются.
- Отдых: крупный отсчёт, ±30 секунд, «Пропустить отдых». Окончание/изменение таймера привязано к абсолютному времени.
- Завершение тренировки с подтверждением и числом незаписанных подходов. Черновики не становятся выполненными автоматически.
- Короткие понятные статусы: «Сохранено на часах», «Отправлено», «Нет сети — записи сохранены», «Нужно восстановить подключение».

Подсказки из истории не обязательны в первом выпуске: использовать уже сохранённые значения и предыдущий выполненный подход текущей тренировки, не выдавать план за факт. Загружать весь архив ради пары значений не нужно.

### Телефон

- Настройки подключения/отзыва часов; кнопки передачи и возврата управления.
- Во время работы часов — просмотр переданной сессии и серверных результатов с индикатором давности.
- Проверка ограничения не только на кнопках: все пути изменения сессии, включая таймер, черновики, замену оборудования/упражнения, завершение, историю и разрешение конфликта, должны учитывать владельца управления.
- Остальные программы и история доступны как обычно. Незавершённую офлайн-сессию с часов не маскировать запуском второй тренировки.

### В последующих версиях, после проверки пользы

Пульс, калории, кольца активности, собственная HealthKit-тренировка, виджет/усложнение циферблата, новая тренировка офлайн с часов, автоматические подсказки прогрессии, нативное приложение iPhone с WatchConnectivity. Они не нужны для проверки записи подходов и не должны задерживать её.

## 6. Сохранение и синхронизация

### Один редактор переданной тренировки

Полные снимки текущего протокола удобны для первого клиента, если в каждый момент сессию редактирует одна сторона. Вводим серверную запись управления отдельно от JSON Session: `sessionId`, `owner`, `state`, `deviceId`, монотонный `controlEpoch`, идентификатор передачи. Состояния: телефон, предложение часам, часы. Завершённая сессия освобождает управление после синхронизации.

Блокировка относится к серверной учётной записи и сессии, а не только к одной вкладке. `controlEpoch` защищает от запросов часов, отправленных после принудительного возврата управления.

Передача:

1. PWA прекращает новый ввод, дожидается очереди черновиков и ошибок локального сохранения. Не допускать deadlock: не вызывать `syncOnce()` внутри уже удерживаемого `traininglog-sync`; выделить внутренний метод либо оркестратор с единым порядком блокировок.
2. Отправляет свою копию, повторяет потерянные ответы, проверяет отсутствие конфликта, чистую локальную копию и подтверждённый `baseVersion`.
3. Сервер атомарно сверяет поколение/версию, отсутствие другого владельца и создаёт предложение конкретным часам. Новые записи браузеров в эту сессию запрещаются уже сейчас.
4. Часы скачивают снимок, проверяют поддерживаемость данных, сохраняют его на диск, затем принимают предложение. Сервер переводит управление часам. Часы сохраняют подтверждённые epoch/version до включения редактирования.
5. При потере ответа приёма часы запрашивают состояние передачи. Не начинают запись по одному предположению, что запрос мог пройти. Повторы передачи идемпотентны.
6. Непринятое предложение можно отменить или ограничить коротким сроком; отмена и приём конкурируют в одной транзакции. Уже принятая офлайн-сессия **не возвращается телефону автоматически по тайм-ауту**.

Любая смена управления увеличивает серверную версию сессии и добавляет запись Changes, даже если пользовательский payload не поменялся. Это инвалидирует старые PUT. Управление выдаётся отдельными метаданными; их нельзя переписать через импорт JSON или обычный Session payload.

Сервер блокирует обычный `PUT sessions/{id}` во время передачи/владения часами, включая старые версии PWA. Возвращает различимый ответ `423 session_controlled_by_watch` с безопасными метаданными. Веб-клиент должен продолжать чтение Changes при заблокированной очереди, сохранять грязную копию отдельно, не зацикливаться на повторе PUT и не терять другие документы.

Состояние передачи хранить и в IndexedDB телефона: перезагрузка страницы или отсутствие сети не снимает известную блокировку. При открытии/возврате из фона сначала сверять серверное управление и принимать новую версию сессии, затем разрешать запись. Для новой таблицы управления использовать следующую версию Dexie после фактической текущей (сейчас v4), сохраняя старые данные и очереди.

После возврата нужно сначала получить актуальный снимок и состояние управления. Старый браузер с накопленными изменениями получает обычный конфликт версий; принудительная перезапись без сохранения обеих копий не разрешается. Офлайн-редактирование неизвестной старой вкладкой нельзя физически предотвратить, но оно не должно затереть принятые сервером результаты.

### Локальное хранилище часов

- Один сериализованный Swift actor управляет тренировкой, записью файла и отправкой. UI работает через него.
- Храним целую Session, базовую подтверждённую копию и серверную версию, generation/epoch, локальную ревизию, выбранные UUID, неподтверждённый неизменяемый HTTP-запрос и статус возврата/завершения.
- Для первой версии достаточно атомарного файла в Application Support с версией формата и предыдущей валидной копией; UserDefaults использовать только для небольших предпочтений. Успех записи показывать после завершения сохранения. Ошибка диска оставляет подход на экране с возможностью повторить.
- Секрет устройства хранится отдельно в Keychain. Он не попадает в JSON-экспорт, логи или репозиторий.
- После перезапуска восстанавливаем состояние с диска; неизвестный формат или повреждение не трактуем как пустой дневник.
- Очередь строится из снимков, а не из нажатий «+». Несколько ещё не отправленных правок можно объединить. Уже подготовленный/отправленный запрос запрещено менять.
- Потерянный ответ повторяется с прежними `operationId`, payload, generation, epoch и baseVersion. Позднейшие локальные изменения остаются отдельно; старый ответ не заменяет новый черновик.

### Серверная запись часов

Добавить узкий endpoint записи закреплённой сессии. Использовать существующий механизм транзакций Documents/Changes/Operations через общий сервис, с тем же writer gate для браузеров, часов и смены управления. Независимый semaphore на новом маршруте не обеспечит общую сериализацию.

Запрос: версия watch-протокола 1, `contractVersion: 2`, `operationId`, `baseVersion`, `generation`, `controlEpoch`, полный `payload` Session. Сервер определяет владельца/устройство по токену, а не верит полям запроса.

Проверки: авторизация и отзыв устройства, область доступа, поколение, сохранённая квитанция повтора, право управления, версия документа, формат Session и допустимые изменения. Квитанция успешного повтора доступна тому же устройству даже после обычного возврата, но отозванному токену доступ не возвращается. Хеш квитанции включает маршрут/операцию, сессию, устройство, epoch и неизменяемое тело; разные операции не делят случайно один receipt.

Часы могут менять записи подходов, отдых, локальную ревизию и разрешённый переход статуса. Они не меняют программу/день, UUID, порядок/состав упражнений, профиль оборудования, архив/корзину или даты начала. Данные вне разрешённых изменений должны совпадать с базой. Повторно использовать общую валидацию и добавить проверку допустимого diff; наличие синтаксически валидного JSON само по себе недостаточно.

Неизвестные JSON-поля сохранять при round-trip. Swift DTO, который декодирует только видимые поля и потом заново кодирует документ, может стереть данные. Нужен исходный JSON с типизированным доступом и изменением известных путей, либо явное хранение дополнительных полей. Неизвестное значение значимого enum блокирует запись с понятным сообщением о совместимости.

Отправка — сразу после локального сохранения при доступном приложении, при возврате на экран и вручную. Ошибки сети: повтор с ограниченной экспоненциальной задержкой и jitter; 401/403: сохранить очередь и показать восстановление подключения; 409: сохранить обе копии; 429: учитывать Retry-After. Фоновую доставку к определённому сроку не обещать.

PWA при наблюдении за переданной тренировкой может опрашивать сервер каждые 3–5 секунд только на видимом экране; при скрытии/ошибках снижать частоту. Обычный режим сохраняет текущую частоту. WebSocket не нужен для первой версии.

### Возврат, завершение и аварийное восстановление

Нормальный возврат: часы блокируют дальнейший ввод, сохраняют намерение, доставляют последнюю копию, затем идемпотентно освобождают управление с точной версией/epoch. До подтверждения показывают ожидание. Повтор после потери ответа не создаёт новую передачу.

Завершение: часы сохраняют завершённую сессию офлайн; сервер после получения финального снимка атомарно завершает владение. Квитанция повторного финального PUT возвращается без повторного завершения. Сопутствующие изменения, которые сейчас выполняет `App.tsx` при finish, проверить отдельно: календарь/итоги/навигация не должны незаметно зависеть только от нажатия кнопки в PWA. Определить один идемпотентный путь для обоих клиентов.

Принудительный возврат с телефона — отдельное явное действие владельца. Показать время последнего снимка и предупредить о возможных неотправленных подходах. Сервер архивирует текущую версию, увеличивает epoch/version и запрещает дальнейшие записи старого владельца. Поздняя офлайн-копия часов сохраняется как материал восстановления, не становится текущей автоматически.

Предусмотреть защищённую загрузку восстановительного снимка от привязанных часов в отдельный архив, не в активную сессию. При отзыве/истечении токена сначала новая привязка; при переподписи локальную копию не стирать. На телефоне можно скачать и сопоставить копии, используя существующий механизм архива конфликтов. Смена generation после восстановления серверной базы также требует сверки, а не автоматической перезаписи.

## 7. Привязка и API

В настройках авторизованной PWA владелец создаёт одноразовый восьмизначный код. Код действует 5 минут, потребляется атомарно, имеет ограничение попыток; есть ограничения частоты выпуска и обмена по устройству/адресу и общему бюджету. Уникальность активных кодов проверяется сервером. Часы вводят код один раз и получают криптографически случайный токен не менее 256 бит. На сервере хранится хеш токена, владелец, deviceId, даты выдачи/истечения и отзыв.

Токен действует 90 дней, продление через повторную привязку с сохранением данных. Это наше проектное решение, независимое от 7-дневной подписи Apple. Потерянный ответ обмена кодом решается новым кодом; не оставлять доступный долгоживущий токен по короткому коду. В списке устройств показывать время последнего обращения и возможность отзыва. Смена пароля владельца должна отзывать токены часов; обычный выход из PWA — нет.

Предлагаемые маршруты под `/training/api` (уточнить имена при записи OpenAPI, смысл зафиксирован):

- Cookie + CSRF: `POST /watch/pairing`, `GET /watch/devices`, `DELETE /watch/devices/{id}`; создание кода, список и отзыв.
- Без cookie, с отдельным rate limit: `POST /watch/pairing/redeem`; единственный публичный обмен короткого кода на токен.
- Cookie + CSRF: `POST /sessions/{id}/watch-handoff`, `POST /sessions/{id}/watch-handoff/cancel`, `POST /sessions/{id}/watch-force-return`.
- Cookie авторизация: `GET /sessions/{id}/watch-control`; состояние для PWA, без секретов.
- Cookie авторизация: `GET /watch/recovery` и `GET /watch/recovery/{id}`; список восстановительных копий владельца и скачивание для сравнения. Принятие выбранной копии проходит текущую проверку версии/управления и архивирование обеих сторон, а не безусловную замену.
- Watch bearer: `GET /watch/v1/session`, `POST /watch/v1/handoff/accept`, `PUT /watch/v1/sessions/{id}`, `POST /watch/v1/control/release`, `POST /watch/v1/recovery`.

Маршруты записи и управления получают idempotency key и ожидаемые epoch/version там, где это требуется. GET сессии отдаёт только назначенную этому устройству тренировку, метаданные управления и поддерживаемые версии протокола. Выбор текущего подхода можно передать как подсказку UUID в handoff, не менять из-за него бизнес-формат Session.

Текущий глобальный CSRF middleware проверяет **все** POST/PUT/DELETE. Его нужно изменить осознанно: cookie-маршруты продолжают требовать CSRF, строго bearer-only watch-маршруты используют отдельную схему авторизации без cookie fallback; исключение для redeem ограничено ровно этим endpoint и защищено одноразовым кодом/rate limit. Не отключать CSRF целиком и не обходить проверку просто по наличию заголовка Authorization.

Токен часов не даёт экспорт всего дневника, управление паролем, программами, оборудованием и другими сессиями. Все запросы HTTPS; bearer не передавать на другой origin при редиректе. Логи исключают код, токен, пароль и полное тело с личными записями. Это часть новой функции привязки, а не отдельная переделка всей системы безопасности.

Повторная привязка не наследует права активного устройства по переданному с часов `deviceId`. Связь с прежним устройством/сессией подтверждает авторизованный владелец в PWA. Восстановительный endpoint допускает загрузку локальной копии после такой привязки, но не даёт токену читать произвольные документы; ограничить размер/число копий и устранять дубликаты по idempotency key.

## 8. Таймер и ограничения watchOS

Отсчёт рисуем как `max(0, restEndsAt - now)`. Не храним «оставшиеся секунды», уменьшаемые фоновым циклом. На возобновлении приложения время пересчитывается.

При каждом подтверждении/изменении отдыха локально планируем одно уведомление по стабильному идентификатору сессии; старое отменяем. Пропуск/завершение снимает уведомление. В открытом приложении — короткий haptic, в фоне — системное локальное уведомление. Согласовать два пути, чтобы не было двойного сигнала. Уведомления зависят от разрешений, Focus, беззвучного режима и настроек часов. [Apple: локальные уведомления](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app), [уведомления watchOS](https://developer.apple.com/documentation/watchos-apps/notifications)

Первая версия не обещает постоянно держать приложение активным, возвращать его на каждый подъём запястья или непрерывно выполнять произвольный код после выключения экрана. Не включать фоновые аудио/геолокацию ради таймера и не выдавать силовую тренировку за другой тип extended runtime session. Если потребуется интеграция HealthKit, отдельно проверить бесплатное подписание и сосуществование со штатной «Тренировкой». [Apple: extended runtime](https://developer.apple.com/documentation/watchkit/using-extended-runtime-sessions)

Проверить отдых при погашенном экране, на циферблате, со штатной тренировкой Apple, при включённом Focus и отказе в уведомлениях. Корректный отсчёт и сохранность подходов обязательны; вибрация в каждом режиме — результат физической проверки, а не гарантия симулятора.

## 9. Последовательность реализации и файлы

Этапы выполнять по порядку. До этапа 0 не строить большую интеграцию.

### Этап 1 — проект и локальная тренировочная логика

Создать `apps/watch/TrainingLogWatch.xcodeproj`, shared scheme и приложение SwiftUI. Использовать штатный шаблон Xcode и системные framework, без обязательного XcodeGen/CocoaPods/стороннего сервиса. Deployment target выбрать по реальной watchOS пользователя.

Внутри `apps/watch` выделить Foundation-модуль `WorkoutCore` (локальный Swift package) для модели, сохранения, порядка подходов и sync state machine; UI и UserNotifications оставить в watch target. Тесты Core запускать на Mac без подписи. Минимальная структура: `WorkoutCore/`, `TrainingLogWatch/`, `TrainingLogWatchTests/`, `Config/`, `README.md`.

Добавить общие фикстуры под `tests/contracts/watch/`: обычная сессия, суперсет, односторонние упражнения, длительность, помощь весом, нерегулярные деления, обязательное оборудование, неизвестные поля. На TypeScript и Swift прогнать одинаковые входы/ожидаемые результаты. Учитывать fallback `restOf`, а не только поле rest.

Сначала локальные данные из фикстуры, атомарное сохранение, повторный запуск и базовые экраны; затем сеть. Team ID, подписи, UDID и локальные настройки не фиксировать в общих файлах. Добавить в `.gitignore` DerivedData, xcuserdata, локальный xcconfig, provisioning profiles и локальные секреты.

Готово, когда тренировку из фикстуры можно полностью пройти и восстановить после закрытия без сети.

### Этап 2 — серверные примитивы и контракт

Вынести общую запись документов из `Program.cs` в небольшой сервис, сохранив поведение v2. Добавить таблицы привязок/кодов/управления/восстановительных снимков и миграцию; receipt можно расширить или отделить для watch, но все записи используют одну транзакционную модель и общий gate.

Реализовать привязку, scopes, передачу, scoped GET/PUT, возврат, отзыв и восстановление. Добавить watch API в `openapi.json`, перегенерировать `api.generated.ts`, добавить отдельную версию watch-протокола без скрытого изменения существующего v2. Не включать функцию на рабочем сервере до проверки совместимости старой PWA.

Готово, когда API-тесты подтверждают единственного редактора, идемпотентность, отсутствие обхода через старый PUT и сохранение неподдержанных/конфликтующих копий.

### Этап 3 — PWA и часы с сервером

Добавить веб-модули `watchApi.ts`, `watchControl.ts`, `WatchSettings.tsx`, подключить к `SettingsScreen.tsx`, `App.tsx`, `WorkoutScreen.tsx`, `data.ts`, `sync.ts`, `useSyncController.ts`. Точные имена можно уточнить, сохранив явное разделение UI/передачи/синхронизации.

На часах добавить Keychain, URLSession-клиент, pairing UI, actor синхронизации и приём сессии. Реализовать восстановление ответа handoff и последней отправки после перезапуска. Провести полный сценарий на изолированной локальной базе.

Готово, когда одна и та же сессия проходит путь телефон → часы → сервер → телефон, сохраняя UUID, значения, порядок, даты и количество подходов, а потеря сети не блокирует ввод.

Готово, когда пройдены обязательные сценарии из раздела 10. Затем пользователь может попробовать реальную тренировку после установки совместимой серверной версии.

Добавить инструкции и небольшой `scripts/watch-install.sh`: проверка Xcode/SDK, текущего устройства/схемы, сборка и установка подходящими для установленного Xcode инструментами. Сначала надёжный ручной Run в Xcode; script автоматизирует только проверенный путь. Не зашивать несуществующий destination/UDID и не обещать универсальный devicectl для любой версии watchOS.

Инструкция должна позволять повторить установку поверх приложения с тем же team/bundle ID и проверить локальные записи. Внешние покупки, публикация, автоматизации аккаунта и смена региона не входят в эту работу.

## 10. Проверки и критерии готовности

Обязательные автоматические сценарии:

1. Паритет Swift/TS: граммы без float-ошибок, десятичная запятая, повторы/секунды, RIR, стороны, собственный/добавочный/помогающий вес, шаги и деления, rest defaults, суперсеты.
2. Двойное нажатие и повтор HTTP после потерянного ответа сохраняют один подход; разные тела с одним operationId отклоняются.
3. Правка после отправки, но до ответа, остаётся в локальной копии и отправляется следующей операцией.
4. Передача во время незавершённого ввода/ошибки диска/конфликта не начинается. Потеря каждого ответа prepare/accept/release восстанавливается.
5. Старый/второй браузер не переписывает watch-сессию, включая resolveConflict и восстановленный из JSON дневник. Заблокированный PUT не прекращает чтение серверных изменений.
6. Обычный возврат требует доставки последней копии; принудительный увеличивает epoch. Поздние офлайн-данные сохраняются отдельно, не затирают текущую сессию.
7. Просроченный/повторный код, перебор, отозванный/чужой токен, доступ к невыданной сессии и cookie-запрос без CSRF отклоняются. Поддельный Authorization не отключает CSRF.
8. Смена generation, несовместимая версия протокола, неизвестные поля/enum, повреждённый файл и завершённая сессия обрабатываются без молчаливой потери данных.
9. Удаление/отзыв устройства при активной сессии сохраняет путь восстановления и не отдаёт старому токену доступ по квитанции.
10. Finish не дублирует календарные/связанные изменения; исправление подхода не создаёт новые UUID; черновики не попадают в статистику как выполненные.

На физических устройствах проверить:

- Запуск без debugger, офлайн-запись нескольких подходов, принудительное закрытие и восстановление.
- Реальное отсутствие интернета на всех маршрутах часов, затем возврат сети; одно выключение Wi-Fi не доказывает офлайн при работающем iPhone/LTE.
- iPhone заблокирован, PWA закрыта; часы продолжают локальную запись, при открытии телефон подхватывает доставленное.
- Уведомление по завершении отдыха и его отмена/перенос, часы на циферблате и в штатной «Тренировке», Focus/отказ в разрешении.
- Обновление поверх установленной сборки сохраняет очередь; bundle ID и team остаются прежними.
- Отдельная проверка после фактического истечения бесплатной подписи и повторного Run. До истечения отметить её как ожидающую, а не пройденную.

Не требовать одного большого набора тестов на каждом изменении. Сначала проверки изменённой части; перед готовым выпуском — Swift Core tests, watch simulator/device build, frontend unit/storage, API-тесты, затронутые E2E/sync, web build/lint/offline.

## 12. Еженедельная переподпись

Планировать обновление за день до истечения, ориентируясь на реальную дату профиля, когда её удаётся прочитать. Если доступна только дата установки, обозначить её как приблизительную оценку. Напоминание в macOS/Календаре можно настроить позже по просьбе владельца; этот документ ничего не создаёт в календаре.

Процедура: открыть тот же проект на Mac → подключить/обнаружить часы → выбрать тот же Personal Team → Run/проверенный install script → проверить открытие тренировки и последнюю синхронизацию. Для получения новой бесплатной подписи может требоваться соединение Mac с Apple и повторный вход/2FA. Фоновую полностью автоматическую переподпись не обещаем.

Обновлять поверх установленного приложения, **не удалять его для переподписи**. Перед плановым обновлением отправить сохранённые тренировки на сервер. Если подпись уже истекла, сначала восстановить запуск поверх старой установки; не сбрасывать контейнер с неотправленными результатами. Сохранение данных после повторной установки нужно подтвердить этапом 0 и физическим тестом.

Веб-дневник не зависит от подписи часов и остаётся доступным. Если управление осталось на недоступных часах, использовать описанный путь восстановления; отсутствие сети или истёкшая подпись не означают, что сервер получил все подходы.

## 13. Выпуск и границы этой задачи

Сейчас разрешено подготовить план. Этот документ не является выполненной разработкой и не меняет рабочий сервер.

При последующем запуске реализации сначала выполняются локальные этапы. Перед первой реальной тренировкой нужно установить совместимые API и PWA на сервер: одна установка watch-приложения этого не заменяет. Подготовить миграцию, резервную копию, результаты локальных проверок и конкретный набор изменений; выполнять выкладку только при наличии авторизации пользователя на неё.

Сначала сервер с feature flag, затем совместимая PWA, затем включение передачи конкретному устройству. Проверить старую PWA и отсутствие работающей watch-сессии перед откатом. При rollback с активным владением сначала доставить/сохранить данные и корректно завершить передачу; старая версия сервера без блокировки не должна принимать параллельные записи. Флаг не отменяет существующее владение и не удаляет базу/очередь.

Считать реализацию готовой, когда физические часы бесплатно установлены, полный сценарий подтверждён на изолированных данных, офлайн-записи переживают перезапуск, сервер защищает единственного редактора и есть воспроизводимая инструкция переподписи. Ожидающий недельный тест отметить отдельно. Симулятор, красивый экран или успешный HTTP health-check по отдельности не означают готовности.

## 14. Как продолжить на Mac

Скачать актуальную зафиксированную версию репозитория, в которой есть этот план и файл-поручение. Если после подготовки передачи появятся новые незакоммиченные изменения, перенести их дополнительно: обычный `git clone` их не забирает. Секреты, Apple-пароль и SSH-ключи не класть в репозиторий; доступ к серверу передавать отдельно только когда он потребуется.

В новой сессии дать поручение из `docs/apple-watch-mac-handoff.md`. Агент должен сначала проверить текущую версию кода и локальные инструкции, затем идти с этапа 0. Уточнение модели часов и окружения делается на Mac по фактам; выбор платного распространения заново не обсуждается, пока сам владелец не изменит ограничение.
