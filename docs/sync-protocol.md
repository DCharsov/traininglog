# Серверная синхронизация — первый выпуск

## Хранилища

IndexedDB v2 добавляет meta (базовая серверная версия и канонический подтверждённый снимок), operations (неизменяемый запрос), syncState (поколение, курсор, подключение) и conflictArchive. Программы, сессии и старый outbox v1 сохраняются. Старый outbox не проигрывается как история: отправляется актуальный снимок. Черновики тоже участвуют в сравнении, даже если не добавили старую outbox-запись.

SQLite: Identity, Documents с ключом owner/kind/id и целочисленной версией, Operations с hash и сохранённым ответом, Changes с неизменяемым снимком каждой версии и монотонным Sequence, Settings/generation. Один процесс и последовательный writer; проверка версии, документ, change и receipt в одной транзакции. Старые версии программы остаются в Changes; уже начатые сессии содержат собственный снимок.

## Контракт

Префикс `/training/api`. JSON; лимит одного запроса 2 МиБ. Ошибки различают 400 validation/csrf, 401 вход, 409 conflict/generation/operation_reused, 429 ограничение входа. API никогда не кэшируется service worker. Изменяющие запросы требуют X-CSRF-TOKEN, полученный из auth/state, включая вход.

- GET auth/state: authenticated, token. Анонимный, данных дневника не выдаёт.
- POST auth/login: {password}; владелец фиксирован, регистрации нет.
- POST auth/logout; POST auth/password: {currentPassword,newPassword}.
- GET bootstrap: {generation}.
- GET changes?after=sequence&generation=uuid: {generation,changes:[{sequence,kind,id,version,payload}],cursor,hasMore}; страницы по 25.
- PUT programs/{id} или sessions/{id}: {operationId,baseVersion,generation,payload}; ответ {version,generation}. payload соответствует текущим схемам программы/сессии в domain.ts.
- GET export: резервная копия schemaVersion=1 с актуальными серверными документами.
- GET health: только состояние сервиса.

Все маршруты с дневником требуют Identity-cookie владельца; Owner берётся из серверного principal. У cookie Secure/HttpOnly/SameSite=Strict, Path=/training/api. Ограничение 10 входов в минуту и блокировка Identity после 5 неудач на 15 минут. Data Protection keys вне веб-каталога.

## Цикл клиента

Синхронизация явно подключается входом. Активный редактор держит Web Lock; синхронизация и restore дополнительно сериализуются отдельным lock. Повторяются уже подготовленные операции, затем читаются изменения, затем отправляются грязные документы. Новый ввод во время запроса остаётся в локальном документе; ответ меняет только подтверждённый снимок в meta. Повтор потерянного ответа использует тот же operationId/payload/baseVersion.

При удалённом изменении грязной записи локальный документ не заменяется, remote сохраняется в meta. Пользователь скачивает сравниваемые варианты и выбирает; оба архивируются перед разрешением. Если пришла другая активная сессия, её принятие ждёт завершения/отмены текущей. Конфликт останавливает отправку именно этого документа. Изменённый во время открытой формы программы шаблон нельзя перезаписать старой версией формы.

Открытие, возврат на экран, online, 30-секундный foreground-интервал и ручная кнопка запускают попытку. Сетевые ошибки увеличивают задержку до 5 минут. 401 показывает повторный вход, сохраняя документы и операции. При выходе локальный дневник сохраняется и автоматическая отправка отключается. Пароль/token не сохраняются в localStorage/IndexedDB.

## Восстановление

Локальный restore заменяет только локальные программы/сессии, очищает сетевые receipt-метаданные и выключает подключение. Серверные данные не удаляются. При следующем входе выполняется сверка с нулевым курсором и явные конфликты для отличающихся UUID.

`scripts/restore-backup.py archive destination` восстанавливает серверный архив только в НОВЫЙ каталог, проверяет SQLite и меняет generation. Не запускается поверх живой базы. При смене поколения клиент сохраняет локальные документы и архивирует старые конфликтные варианты, сбрасывает сетевые базовые версии и повторно читает changes. Старые операции не исполняются в новом поколении.

## Ограничения

Нет API удаления/tombstones, нормализованных каталогов и генерируемого OpenAPI-клиента. Изменения в этом выпуске создаются/обновляются полными снимками. Журнал Changes/Operations пока не обрезается. Это не протокол синхронизации нескольких владельцев: публичной регистрации нет. Автоматический logout не шифрует и не очищает уже намеренно сохранённую локальную базу.

Реализация опирается на [транзакции EF Core](https://learn.microsoft.com/en-us/ef/core/saving/transactions), [optimistic concurrency](https://learn.microsoft.com/en-us/ef/core/saving/concurrency) и [antiforgery ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery?view=aspnetcore-10.0).
# Дополнение: контракт v2

Синхронизируются `programs`, `sessions`, `equipment`, `calendar`. У каждого документа есть необязательные `archivedAt` и `deletedAt`; удаление — новая версия снимка, а не физическое стирание. Очередь, идемпотентность и конфликт-архив работают одинаково для всех четырёх типов. PUT требует `contractVersion:2`, bootstrap сообщает ту же версию. Старые клиенты получают 426 без потери локальных записей. OpenAPI и генерируемые DTO: [release-v2.md](release-v2.md). Базовые правила ниже продолжают действовать.
