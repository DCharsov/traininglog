# Apple Watch v1 — проверка и выпуск

Состояние на 28 сентября 2026: после отдельного разрешения владельца API и PWA
опубликованы, миграция применена, `Watch__Enabled=true`. Перед выкладкой проверены
backup, восстановление и миграция на отдельной копии; рабочие документы не заменялись.
Подробности — [deployment.md](deployment.md). Полный физический HTTPS-прогон
ещё не подтверждён; сообщение владельца «вроде работает» относится к демо.
Bundle ID и Personal Team сохранены. HealthKit, пульс, калории, App Store,
самостоятельное приложение iPhone и создание новой тренировки с часов не добавлены.

## Что реализовано

- `apps/watch/WorkoutCore`: модель с сохранением неизвестных JSON-полей, валидация,
  порядок суперсетов/сторон, вес в целых граммах, профили оборудования, RIR, отдых,
  автоподстановка только пустого черновика и только из текущей тренировки.
- Actor сначала атомарно сохраняет версионированный `workout-state.json`, затем
  публикует изменения интерфейсу. `workout-state.previous.json` сохраняет предыдущую
  валидную копию. Повреждение/неизвестный enum не сбрасывают данные. Выбранный подход,
  передача и неизменяемый подготовленный запрос входят в тот же файл.
- SwiftUI: подключение, приём, подход, отдых ±30 секунд, пропуск, выбор упражнения,
  исправление последнего, RIR/заметка, завершение с подтверждением и возврат.
  Уведомление привязано к абсолютному `restEndsAt`; отказ не блокирует запись.
- Watch bearer-токен в Keychain, сервер хранит только SHA-256; срок 90 дней.
  Подключение без ручного ввода: телефон открывает двухминутное окно, часы создают
  запрос, владелец явно подтверждает совпадающие слова на телефоне. До подтверждения
  токен не даёт доступа; он сохраняется в Keychain до первого запроса, поэтому
  потерянные ответы можно повторить. Старый кодовый API оставлен для совместимости,
  но поля ввода кода в интерфейсе нет. Число запросов и попыток ограничено.
  Cookie-маршруты сохраняют CSRF, bearer не разрешает обход защиты других маршрутов.
- Общий серверный writer/транзакции для браузерных записей, часов и управления.
  Предложение сразу блокирует старые PWA кодом 423. Версии, generation, controlEpoch
  и operationId защищают смену редактора и повторные запросы.
- Приём подтверждается только после записи полного снимка на диск и проверки
  действующего управления на сервере. Потеря сети не передаёт управление телефону.
  Подтверждение отправленного снимка не стирает более новые локальные правки.
- Аварийный возврат архивирует серверную копию; поздняя копия часов загружается
  отдельно. Отозванное/новое подключение не получает право перезаписывать тренировку.
- PWA: привязка/отзыв устройств, передача, наблюдение, отмена/аварийный возврат,
  постоянная IndexedDB-блокировка, архивирование устаревших локальных правок.
  Версия IndexedDB 5, контракт Session/v2 не заменён.

## Как пользоваться после включения API

1. Войти в серверную синхронизацию PWA. В настройках Apple Watch нажать
   «Подключить часы». На часах выбрать «Подключить дневник» → «Подключить».
   Сверить слова на обоих экранах и нажать «Это мои часы» на телефоне. На часах
   ничего вводить не нужно. Не подтверждать запрос с другими словами.
   По умолчанию адрес API рабочий; для испытаний указать **отдельный HTTPS API**.
2. Начать тренировку в PWA и настроить оборудование. В блоке Apple Watch выбрать
   устройство, затем «Продолжить на часах». Не закрывать страницу до сохранения ввода.
3. На часах нажать «Принять тренировку». Дождаться доступного экрана подхода:
   текст о локальном сохранении до подтверждения сервера ещё не разрешает офлайн-ввод.
4. Первый подход ввести вручную. После выполнения нажать «Готово»; следующий пустой
   подход получит прежние значения. При необходимости открыть поле и изменить их.
   Для собственного веса килограммы не нужны. RIR и заметка всегда отдельные.
5. При сети изменения отправляются автоматически в открытом приложении. Для фоновой
   гарантированной синхронизации watchOS задача не регистрируется: открыть приложение
   и дождаться отправки перед возвратом/выключением. Закрытая PWA также не обязана
   обновляться в фоне.
6. «Вернуть на телефон» замораживает ввод и ждёт доставки очереди. Без сети запрос
   остаётся локально. Завершение тренировки пропускает незавершённые подходы.

При аварийном возврате не удалять приложение часов. Открыть его с сетью и сохранить
копию на сервере. Эта команда замораживает текущую копию для восстановления, а не
возобновляет обычную отправку. При истёкшем токене сначала привязать заново. В PWA
скачать восстановительные копии из настроек и сверить перед ручным внесением правок;
автоматического слияния конфликтующих подходов нет.

## Локальные команды (macOS)

Нужны Node.js 24, .NET SDK из `global.json` (10.0.400) и Xcode 26.3.
На этом Mac инструменты установлены локально, без изменения версий проекта:

```sh
export PATH="/Users/dmitrycharsov/Library/Developer/TrainingLogTools/node-v24.21.0-darwin-arm64/bin:/Users/dmitrycharsov/Library/Developer/TrainingLogTools/dotnet:$PATH"
export DOTNET_ROOT="/Users/dmitrycharsov/Library/Developer/TrainingLogTools/dotnet"
export DEVELOPER_DIR="/Applications/Xcode-26.3.app/Contents/Developer"
npm ci --prefix apps/web
npm test --prefix apps/web
npm run build --prefix apps/web
npm run lint --prefix apps/web
dotnet test tests/api/TrainingLog.Tests.csproj -p:RestoreLockedMode=true -p:RuntimeIdentifiers=linux-x64
swift test --package-path apps/watch/WorkoutCore --scratch-path /tmp/traininglog-workoutcore-build
npm run test:e2e --prefix apps/web
npm run test:sync --prefix apps/web
npm run test:offline --prefix apps/web
npm run test:update --prefix apps/web
bash scripts/watch-install.sh simulator-build
```

`RuntimeIdentifiers=linux-x64` сохраняет существующий locked restore сервера;
тестовый процесс исполняется локальным arm64 SDK. API-launcher для Playwright теперь
Node-кроссплатформенный, создаёт свою временную БД вне репозитория и удаляет только её.
Windows использует установленный Edge; macOS — Playwright Chromium и WebKit.
Не направлять sync-тесты на рабочий API. HTTP localhost нужен только браузерным тестам;
приложение часов требует HTTPS и отвергает редиректы.

Общие синтетические данные: `tests/contracts/watch/`; копия демо и справочника отдыха
в ресурсах WorkoutCore проверяются на совпадение. Изменив правила PWA, обновить и Swift.
OpenAPI: `npm ci --prefix tools/api-contract`, затем
`npm run generate --prefix tools/api-contract`.

## Результаты локальной проверки

- WorkoutCore: 16 тестов, включая полные 19 синтетических подходов с новым экземпляром
  хранилища после каждого, сбой записи, повреждение файла, офлайн-очередь, поздние правки,
  повтор принятия после принудительного возврата и запрет отправки демо.
- API: 20 тестов; watch-сценарии на отдельных временных SQLite БД, включая подключение
  без кода, конкурирующие
  передачи и отзыв токенов/неиспользованных кодов при смене пароля.
- Web: 119 unit/storage тестов. TypeScript/production build проходят.
- Обычные браузерные проверки: 50 passed (Chromium/WebKit).
- Sync: существующий сценарий двух браузеров и новый телефон → эмуляция watch API →
  сервер → телефон и подключение без кода проходят. Это не физический HTTPS-прогон часов.
- Offline: 2 passed. Update: 11 passed, 1 skipped (существующий WebKit cold restart).
- Lint: ошибок нет, шесть прежних React-предупреждений. Сборка предупреждает о JS-чанке >500 КБ.
- Симулятор watchOS 26.2 / 44 мм: вручную введены 12,5 кг × 10, подтверждён первый
  подход, появился отдых, второй подход получил 12,5 × 10 без повторного ввода;
  после завершения процесса и повторного запуска выбор и значения сохранились.

## Порядок выкладки (первый выпуск разрешён и опубликован 28 сентября)

1. Подготовить отдельный HTTPS-стенд/БД и завершить физический чек-лист выше.
2. Сделать согласованную SQLite-backup существующим `scripts/server-backup.py`,
   сохранить конфигурацию/ключи Data Protection, предыдущие API/frontend releases.
   Проверить восстановление на отдельной копии, не на рабочей БД.
3. Опубликовать API с `Watch__Enabled=false` (по умолчанию false). При запуске
   применяется миграция `20260928113834_WatchControl`: таблицы WatchDevices,
   WatchPairings, WatchControls, WatchRecoveries; существующие документы не переписываются.
   Проверить health, cookie/CSRF и обычную синхронизацию; привязка/новые передачи выключены.
4. Опубликовать совместимую PWA, сохранив прежние hashed assets. Дождаться обновления
   на телефоне. Установить подписанную watch-сборку с прежним bundle ID и Team.
5. Только затем включить `Watch__Enabled=true`, перезапустить API и проверить реальные
   подключения. Синтетические тренировки не загружать в рабочую историю.

Откат: сначала отключить новые передачи флагом. Флаг **не снимает** уже существующие
блокировки и не отзывает токены: действующие часы должны иметь возможность отправить
данные и вернуть управление. Не откатывать API на версию без серверных watch-блокировок,
пока есть `offered/watch` или неотправленные копии. Не удалять watch-таблицы. Сохранить
обе конфликтующие копии до любого ручного восстановления. Восстановление всей БД
меняет generation; часам потребуется восстановительная копия, а не слепой повтор PUT.
