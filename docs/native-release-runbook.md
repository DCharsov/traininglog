# Выпуск нативного дневника и офлайн-резерва

Это инструкция подготовки, не разрешение на изменение рабочего сервера.
Текущий выпуск не готов к включению всех функций: открытые проверки перечислены
в `native-health-progress.md`. Синтетические данные использовать только в демо
или отдельной тестовой БД.

## Перед выпуском

1. Зафиксировать состав выпуска и результаты Swift, TypeScript, API и сборок.
   Проверить не только чистое создание БД, но и переход с WatchLinkApproval на
   WorkoutReservations. Тест ReservationMigrationTests проверяет сохранность
   документов, версии, generation, токена устройства, lease и operation receipts.
2. Завершить физические проверки с сохранённой очередью на iPhone/Series 8,
   единственной записью HealthKit и повторным стартом после потери ответа.
   Разрешения здоровья подтверждает владелец. Никаких значений здоровья в логах.
3. Проверить прежние bundle ID и подпись обоих приложений через
   `bash scripts/verify-native-signing.sh /absolute/path/to/TrainingLogWatch.app`.
   Проверка также сверяет команду с игнорируемым Signing.local.xcconfig и
   действительность обоих provisioning profiles. Отказ этой проверки не обходить:
   пересобрать с прежней командой. Проверка даты не заменяет физический запуск
   после фактического истечения бесплатной подписи.
   Устанавливать поверх, не удалять приложение. Успешная установка iPhone не
   является подтверждением установки встроенного приложения на часах.
4. Получить отдельное разрешение владельца на серверную выкладку и её окно.

## Порядок включения

1. На тестовой БД проверить миграцию и восстановление резервной копии.
2. Перед production-выпуском сохранить проверенную резервную копию SQLite и
   конфигурации, текущий путь API/PWA release и журнал версий миграций. Копия БД
   должна создаваться штатным SQLite backup-механизмом, а не копированием одного
   файла работающей WAL-базы. Не помещать копии и ключи в wwwroot или репозиторий.
3. Выкатить совместимый API с `Watch:ReservationsEnabled=false` (переменная
   окружения `Watch__ReservationsEnabled=false`). Существующий `Watch:Enabled`
   не отключать: он обслуживает текущие передачи. Новая миграция добавляет таблицу
   резерва; существующие Session v2 не переписываются.
4. Проверить health/bootstrap, вход, чтение существующей истории и обычную
   синхронизацию без создания тестовых личных тренировок. Убедиться, что
   `/watch/reservation` сообщает `enabled=false`.
5. Установить совместимые приложения iPhone/Watch и PWA; проверить фактические
   версии на обоих устройствах. Сохранять предыдущие assets для старых клиентов.
6. Включать `Watch__ReservationsEnabled=true` только после прохождения
   сквозного сценария на отдельном окружении и отдельного подтверждения владельца.

## Остановка функции и откат

- Выключение ReservationsEnabled запрещает создание новых резервов, но не
  отменяет существующие. API должен продолжать принимать готовность, старт,
  завершение и восстановительные копии уже подготовленных тренировок.
- После появления резерва нельзя откатывать API на версию, которая не проверяет
  резерв при обычной записи Session: старый сервер может выдать второе право
  редактирования офлайн-тренировки. Сначала отключить новые резервы, сохранить
  копии, завершить/явно отменить существующие и сверить очереди устройств.
- Не выполнять Down-миграцию с удалением WorkoutReservations на рабочей БД.
  Предпочтителен совместимый исправляющий выпуск. Автоматический откат бинарника
  в update-api-cleargate.py не доказывает безопасность отката схемы или полномочий.
- Восстановление старой БД требует нового generation; старые записи клиентов
  должны отклоняться и сохраняться для сверки. Не переписывать generation или
  controlEpoch на клиентах ради обхода конфликта. После такого восстановления
  отдельно проверить доступность отмены старых резервов и восстановление обеих
  локальных копий; этот сценарий ещё не прошёл полный сквозной аудит.

## Что фиксировать в отчёте

Версии сборок, время установки, migration ID, состояние флагов, результаты тестов,
подтверждения неизменности UUID/очереди и наличия одной записи HealthKit.
Не включать медицинские значения, токены, cookies и содержимое личных тренировок.
Проверку запуска после фактического истечения бесплатной подписи оставить
отдельным ожидающим пунктом до наступления этого события.
